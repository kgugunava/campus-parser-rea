# Парсер РЭУ им. Плеханова

Парсер расписания для РЭУ им. Плеханова (`rea`), сделан на основе
[campus-parser-template](https://github.com/campus-mobile/campus-parser-template) с использованием
[campus-parser-kotlin-sdk](https://github.com/campus-mobile/campus-parser-kotlin-sdk). Источник данных —
[rasp.rea.ru](https://rasp.rea.ru/).

## Setup

Для запуска на локальной машине требуется:

1. Наличие [JDK 11](https://jdk.java.net) или выше (`app`-модуль дополнительно требует JDK 17 через свой
   Gradle toolchain).
2. Создать на GitHub PAT-токен с правами `read:packages` — без него не резолвятся зависимости
   (`parser-sdk`, `parser-tests-sdk`), они лежат в приватном GitHub Packages репозитории.
3. Добавить в `gradle.properties` (файл не коммитится, см. `.gitignore`) строку:
   ```
   github.token=<ваш PAT>
   ```

## Development

Для проверки, что всё корректно настроено, можно запустить задачу `build`:

- Windows — `gradlew.bat build`
- Unix/macOS — `./gradlew build`

`BUILD SUCCESSFUL` значит, что проект скомпилировался и все тесты прошли.

Для разработки удобен [IntelliJ IDEA](https://www.jetbrains.com/idea/) (подойдёт и Community Edition) —
в ней есть все интеграции с Kotlin и Gradle. Описание того, как устроены парсеры Campus в целом, — в ридми
[parser-sdk](https://github.com/campus-mobile/campus-parser-kotlin-sdk); там же лежит эталонный пример
`samples/spbstu-parser`, на который я ориентировался при реализации.

При изменении парсера стоит проверять работу через тесты (`src/test`) — так можно отладить парсер на разных
расписаниях без реальных запросов к сайту.

## Testing

Для полноценного прогона парсера есть тестовое приложение в модуле `app`. В `Main.kt` — обычная функция
`main`, можно запустить её прямо из IDEA (стрелка у функции) или через `java -cp <classpath> ru.campus.MainKt`.
Парсер выполняет полную работу, кроме отправки данных на сервер Campus — вместо этого всё, что должно было
бы уйти на сервер, сохраняется в `app/dump/` (по паре файлов на группу: сущность и расписание), а полный лог
прогона пишется в `app/log4j2.log`.

## Парсер РЭУ им. Плеханова — проблемы и как решал

У сайта нет JSON API (в отличие от эталонного `spbstu-parser` из SDK) — почти всё приходится вытаскивать из
HTML-фрагментов через `jsoup`. Ниже — реальные проблемы, с которыми столкнулся по ходу, в порядке их
появления, и как каждая была решена. Раздел про надёжность на нагрузке (п.6) получился самым длинным — он
занял большую часть времени работы над задачей, поэтому описан подробно, шаг за шагом, а не только финальным
решением.

### 1. Сайт — не SPA и не JSON API, а server-rendered HTML-фрагменты

Первое, что показалось подозрительным: на странице нет `fetch`/JSON-ответов в духе `spbstu-parser`. Разобрал
`Scripts/main.js` и нашёл реальные AJAX-эндпоинты (`/Schedule/SearchBarSuggestions`, `/Schedule/Navigator`,
`/Schedule/ScheduleCard`, `/Schedule/GetDetailsById`) — все, кроме первого, отдают HTML-партиалы, а не JSON.
**Решение**: парсить их через `jsoup` (CSS-селекторы по классам/атрибутам вместо `kotlinx.serialization`), как
и предполагает шаблон, только без промежуточных DTO-моделей под JSON — они здесь просто не нужны.

### 2. `SearchBarSuggestions` — не годится для полного списка групп

Единственный настоящий JSON-эндпоинт сайта. Возвращает и группы, и преподавателей одним списком без явного поля
типа, но **всегда не больше ~10 результатов** — годится только под автокомплит поиска, не под перечисление всех
групп вуза. Пришлось искать другой путь для `EntitiesCollector` — см. следующий пункт.

### 3. Обход `Факультет → Курс → Уровень → Группа` не работал через curl — заголовок X-Requested-With

Список групп на сайте собирается через каскадные `<select>`, подгружаемые по одному `POST /Schedule/Navigator`.
Реконструировал запрос по JS-коду (те же поля формы) и раз за разом получал в ответ **ту же самую пустую форму**,
как будто сервер вообще не видел моих данных — при том, что `curl` возвращал `200 OK`.

Проверил несколько гипотез по очереди (CSRF-токен в скрытом поле — не нашёлся; `multipart/form-data` вместо
`urlencoded` — не помогло) — ни одна не объясняла поведение. Решающим оказался **живой перехват реального запроса
через браузер** (Chrome DevTools + перехват `XMLHttpRequest.send` скриптом на странице): выяснилось, что

- реальный запрос — `multipart/form-data`, но **включает только уже пройденные поля цепочки** (Курс/Уровень/
  Группа не передаются вовсе, пока до них не дошли — не как `"na"`, а вообще отсутствуют в теле запроса);
- **обязательно** нужен заголовок `X-Requested-With: XMLHttpRequest` — без него сервер отвечает `302 Redirect`
  (обычный сценарий обработки формы), а не HTML-партиалом с данными. Именно этого заголовка не хватало во всех
  моих попытках через `curl`, и именно поэтому обход не двигался дальше пустой формы.

После этой находки перечисление групп заработало полностью: **1012 реальных групп** со всех факультетов за один
прогон.

### 4. Финальный шаг (выбор группы) не идёт через `Navigator`

Оказалось, что цепочка каскадных запросов — только 3 шага (Факультет → Курс → Уровень), а сам список групп уже
приходит в ответе на 3-й шаг. Выбор конкретной группы — это не ещё один `Navigator`-запрос, а прямой переход к
`ScheduleCard`. Сначала реализовал (неправильно) 4 уровня вложенности — упростил до трёх после того же перехвата
через браузер.

### 5. У группы преподаватель не приходит вместе с расписанием

`ScheduleCard` отдаёт таблицу пар (предмет/время/аудитория/тип), но **без ФИО преподавателя** — оно есть только в
отдельном ответе `GET /Schedule/GetDetailsById?id=<data-elementid>`, по одному запросу на занятие. Значит, на
каждую пару в расписании группы может понадобиться ещё один HTTP-запрос.

**Решение**: кэширование по `elementId` на время жизни коллектора (`ConcurrentHashMap`) — одна и та же
потоковая лекция встречается в расписании многих групп, повторно её запрашивать не нужно.

### 6. Сайт нестабилен под нагрузкой — самая долгая часть работы

Заняло больше всего итераций из всей задачи. Коротко — что пробовал и что в итоге сработало.

**Первый симптом**: единичные таймауты на `GetDetailsById` даже после встроенных в SDK повторов. 

**На полном прогоне стало хуже**: SDK-шный `parallelProcessing` гонит до 10 групп параллельно, и сайт под такой
нагрузкой начал массово падать даже на простых запросах. Завёл `Semaphore`, но сперва обернул им отдельные
HTTP-вызовы, а не группу целиком — из-за этого все 10 групп перехватывали единственный слот по кругу, и ни одна
не успевала завершиться. Перенёс `Semaphore` на уровень всей `collectSchedule()` — группы стали обрабатываться
последовательно, и это сразу дало результат: **8 групп, 0 ошибок, 94.3% успешных запросов**. Заодно разделил
бюджет ретраев (длинный — для первого запроса группы, короткий — для всего остального), иначе один
гарантированно мёртвый `id` занятия стоил бы 3+ минуты впустую.

На 8 группах всё работало, но при масштабировании до **30 групп** та же настройка резко деградировала — 1-2
сохранённых группы за десятки минут. Дальше перепробовал по очереди: короткий таймаут для критического запроса
(помогло чуть быстрее реагировать); общую "передышку" на все группы с эскалацией паузы при повторных
срабатываниях (контрольные прогоны показали, что **даже 5 минут тишины не снижали процент неудач после
паузы** — раз пауза не коррелирует с восстановлением, это чистые накладные расходы, убрал целиком); короткий
`keepAliveDuration` в пуле соединений OkHttp — **единственный фикс, давший измеримый сдвиг сам по себе**
(нашёл через сравнение: пока клиент висел на таймауте, ручной `curl` на тот же URL отвечал за 0.15 сек — дело
было в протухшем соединении из пула, а не в сайте); `Connection: close` и джиттер выхода из паузы — ноль
дополнительного эффекта; `permits=1` без всякого параллелизма — тоже сам по себе не изменил картину.

Сработала независимая сессия на каждую группу: написал `ResettableCookieJar` и стал сбрасывать cookie перед
каждой новой группой, чтобы с точки зрения сайта она выглядела новым визитом, а не продолжением одной долгой
сессии (работает только вместе с `permits=1` — общий cookie jar один на весь `HttpClient`). Первый сбой стал
происходить заметно позже (~2:20 вместо стабильных ~40 сек) — часть деградации была завязана именно на сессию.
Детальный разбор одного эпизода показал: подряд проваливались запросы к совершенно разным ресурсам в течение
~100 секунд, уже при `permits=1` и свежей сессии — похоже на настоящий внешний эпизод неотзывчивости, который
клиентской настройкой не убрать. Раз общая передышка не помогает, а только тратит время — убрал её совсем.
Финальная архитектура: `permits=1` + независимая сессия + `Connection: close` + разный бюджет таймаутов, без
какой-либо глобальной блокирующей паузы.

**Настоящая проблема.** Первый прогон новой архитектуры на 30 группах упал с `Exception in thread
"main"`, хотя формально все 30 числились обработанными. Причина: сайт отдал аудиторию `"1"`, а SDK требует
`classroom` длиннее 1 символа и бросает `AssertionError` — а это `Error`, не `Exception`, и SDK-шный
`parallelProcessing` ловит только `Exception`. Ошибка прошла мимо защиты и уронила процесс целиком, каскадом
отменив ещё 11 нормальных групп. Починил на своей стороне: `nullIfTooShort()` подчищает слишком короткие
`classroom`/`type`/`comment`/`building.name` на `null` до создания `Schedule.Lesson`.


**Финальное решение — отложенный повтор вместо потери группы.** Единичные сбои на критическом запросе всё равно
возможны, поэтому вместо потери группы навсегда `ReaParser` теперь делает два прохода: сначала все группы,
потом — только те, что не удались с первого раза, уже после остальных. Время на "остыть" у неудачной группы
берётся не из пустого ожидания, а как побочный эффект полезной работы над остальными. На контрольном прогоне
7 из 30 групп не задались с первого раза — все 7 спаслись повтором: **30/30, 0 ошибок, 95.3% успешных запросов**.

### 7. Номер недели у сайта — свой, не ISO и не чёт/нечет

Сайт нумерует недели последовательно от начала учебного года, а не по международному стандарту (`weekNumber` из
SDK) и не по чётности. Сначала захардкодил дату понедельника 1-й недели вручную (подобрал по пустому ответу
`ScheduleCard?weekNum=1`) — рабочий, но хрупкий вариант, требующий ручного обновления каждый учебный год.
Оказалось, что в этом нет необходимости: запрос с `weekNum=-1` сам резолвит текущую неделю на сервере и
возвращает её реальный номер в скрытом поле `<input id="weekNum">` ответа. Переключился на это — код больше не
зависит от захардкоженной даты.

### 8. Форма обучения и специальность не приходят отдельным полем

`Entity.Extra.educationForm`/`specialty` для группы не покрываются напрямую ни одним полем ответа. Заметил, что
буква сразу после числового префикса в коде группы (`15.28Д-БИО.../26б` / `15.28В-ТПО.../26б`) коррелирует с
формой обучения — подтвердил эвристику (`Д`→"Очная", `В`→"Очно-заочная", `З`→"Заочная") на выборке из 1012
реальных групп разных факультетов. Это эвристика, а не документированное правило сайта — при появлении
незнакомой буквы код возвращает `null`, а не падает.
