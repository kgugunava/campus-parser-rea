# Шаблон парсера для проекта Кампус

## Template

Для настройки шаблона нужно:

1. В `settings.gradle.kts` изменить `rootProject.name` на `campus-parser-<сокращенное имя вуза>`
2. Изменить пакет `ru.campus.parsers.template` на `ru.campus.parsers.<сокращенное имя вуза>`
3. Переименовать `TemplateParser` в `<Сокращенное имя вуза>Parser`
4. Переименовать `TemplateGroupEntitiesCollector` в `<Сокращенное имя вуза>GroupEntitiesCollector`
5. Переименовать `TemplateGroupScheduleCollector` в `<Сокращенное имя вуза>GroupScheduleCollector`
6. Изменить в `build.gradle.kts` строку `campus-parser-template` на название репозитория
7. Убрать `@Ignore` в `DumpParserTest`

## Setup

Для запуска на локальной машине требуется:

1. Наличие [JDK 11](https://jdk.java.net) или выше
2. Создать на github PAT токен с правами read:packages
3. Добавить в gradle.properties параметр github.token= с токеном

## Development

Для проверки что все корректно настроено можно запустить задачу build:

- Windows - `gradlew.bat build`
- Unix/MacOS - `./gradlew build`

В результате выполнения увидите `BUILD SUCCESSFUL` - значит проект скомпилировался и успешно запустил все тесты.

Для разработки рекомендуется использовать [IntelliJ IDEA](https://www.jetbrains.com/idea/) (подойдет и Community
Edition). В ней есть все интеграции с Kotlin и Gradle.

Проект написан на языке [Kotlin](https://kotlinlang.org).

Описание как делаются парсеры доступно в ридми [parser-sdk](https://github.com/campus-mobile/campus-parser-kotlin-sdk).

Важно, что при изменении парсера, нужно проверять работу через тесты (примеры в `src/test`) - таким образом можно
отладить работу парсера на разных расписаниях.

Для выполнения доработок нужно создать ветку в git со своим именем и вести доработки в ней. Когда доработки завершены
на GitHub нужно создать Pull Request из вашей ветки в develop. GitHub проведет автоматические проверки, а позже и
человек проведет code review. После всех необходимых доработок ветка будет слита в develop, а дальше и опубликована
на сервер парсеров, где начнет свою работу.

## Testing

Для запуска полноценного прогона парсера можно использовать тестовое приложение, которое находится в модуле `app`.

В файле `Main.kt` нажмите на стрелку у функции `main` (при работе через IDEA). Парсер выполнит полностью свою работу,
за исключением отправки данных на сервер Campus. Вместо этого все данные, которые должны будут быть отправлены на
сервер, сохраняются в папке `app/dump` для анализа. Также в файле `app/log4j2.log` сохраняется полный лог запуска.

## Парсер РЭУ им. Плеханова — проблемы и как решал

Источник: [rasp.rea.ru](https://rasp.rea.ru/). В отличие от примера `spbstu-parser` из SDK, у этого сайта нет
JSON API — почти всё приходится вытаскивать из HTML-фрагментов через `jsoup`. Ниже — реальные проблемы, с которыми
столкнулся по ходу, и как каждая была решена.

### 1. Сайт — не SPA и не JSON API, а server-rendered HTML-фрагменты

Первое, что показалось подозрительным: на странице нет `fetch`/JSON-ответов в духе `spbstu-parser`. Разобрал
`Scripts/main.js` и нашёл реальные AJAX-эндпоинты (`/Schedule/SearchBarSuggestions`, `/Schedule/Navigator`,
`/Schedule/ScheduleCard`, `/Schedule/GetDetailsById`) — все, кроме первого, отдают HTML-партиалы, а не JSON.
**Решение**: парсить их через `jsoup` (CSS-селекторы по классам/атрибутам вместо `kotlinx.serialization`), как
и предполагает шаблон, только без промежуточных DTO-моделей под JSON — они здесь просто не нужны.

### 2. `SearchBarSuggestions` — не годится для полного списка групп

Единственный настоящий JSON-эндпоинт сайта. Возвращает и группы, и преподавателей одним списком без явного поля
типа, но **всегда не больше ~10 результатов** — годится только под автокомплит поиска, не под перечисление всех
групп вуза. Пришлось искать другой путь для `EntitiesCollector` — см. следующий пункт.

### 3. Обход `Факультет → Курс → Уровень → Группа` не работал через curl — заголовок X-Requested-With

Список групп на сайте собирается через каскадные `<select>`, подгружаемые по одному `POST /Schedule/Navigator`.
Реконструировал запрос по JS-коду (те же поля формы) и раз за разом получал в ответ **ту же самую пустую форму**,
как будто сервер вообще не видел моих данных — при том, что `curl` возвращал `200 OK`.

Проверил несколько гипотез по очереди (CSRF-токен в скрытом поле — не нашёлся; `multipart/form-data` вместо
`urlencoded` — не помогло) — ни одна не объясняла поведение. Решающим оказался **живой перехват реального запроса
через браузер** (Chrome DevTools + перехват `XMLHttpRequest.send` скриптом на странице): выяснилось, что

- реальный запрос — `multipart/form-data`, но **включает только уже пройденные поля цепочки** (Курс/Уровень/
  Группа не передаются вовсе, пока до них не дошли — не как `"na"`, а вообще отсутствуют в теле запроса);
- **обязательно** нужен заголовок `X-Requested-With: XMLHttpRequest` — без него сервер отвечает `302 Redirect`
  (обычный сценарий обработки формы), а не HTML-партиалом с данными. Именно этого заголовка не хватало во всех
  моих попытках через `curl`, и именно поэтому обход не двигался дальше пустой формы.

После этой находки перечисление групп заработало полностью: **1012 реальных групп** со всех факультетов за один
прогон.

### 4. Финальный шаг (выбор группы) не идёт через `Navigator`

Оказалось, что цепочка каскадных запросов — только 3 шага (Факультет → Курс → Уровень), а сам список групп уже
приходит в ответе на 3-й шаг. Выбор конкретной группы — это не ещё один `Navigator`-запрос, а прямой переход к
`ScheduleCard`. Сначала реализовал (неправильно) 4 уровня вложенности — упростил до трёх после того же перехвата
через браузер.

### 5. У группы преподаватель не приходит вместе с расписанием

`ScheduleCard` отдаёт таблицу пар (предмет/время/аудитория/тип), но **без ФИО преподавателя** — оно есть только в
отдельном ответе `GET /Schedule/GetDetailsById?id=<data-elementid>`, по одному запросу на занятие. Значит, на
каждую пару в расписании группы может понадобиться ещё один HTTP-запрос.

**Решение**: кэширование по `elementId` на время жизни коллектора (`ConcurrentHashMap`) — одна и та же
потоковая лекция встречается в расписании многих групп, повторно её запрашивать не нужно.

### 6. Сайт нестабилен под нагрузкой — путь расследования

Это заняло больше всего итераций, поэтому опишу весь путь, а не только финальное решение.

**Первый симптом**: при прогоне одной группы конкретный `GetDetailsById?id=...` несколько раз подряд отвечал
таймаутом (`SocketTimeoutException`), даже после автоматических повторов, встроенных в SDK (`HttpRequestRetry`,
3 попытки с экспоненциальной задержкой) — суммарно процесс ждал ~50 секунд на одном запросе и падал целиком.
Первое решение — обернуть запрос деталей занятия в `try/catch`: если пара не отдаёт детали, она остаётся без
преподавателя вместо потери всей группы.

**На полном прогоне (все ~1012 групп) стало хуже**: `parallelProcessing` из SDK запускает до 10 групп
параллельно — под такой нагрузкой сайт стал массово отвечать таймаутом уже на *любых* запросах, включая
единичный `GET /` без всякой сопутствующей нагрузки. Добавил на уровне `ReaGroupScheduleCollector` собственный
`Semaphore` (сначала permits=3, не помогло — тестовый прогон на 8 группах дал 1 успех / 7 ошибок; уменьшил до
permits=1 — картина не изменилась).

**Только детальный разбор `app/log4j2.log`** (не просто "падает/не падает", а разбивка по эндпоинтам, типам
исключений, и — главное — проверка, помогает ли повтор) показал две разные вещи одновременно:

1. **Запросы на самом деле в основном успешны**: 200 из 209 (95.7%), и *все* 8 неудачных были устранены первой
   же повторной попыткой — ни одного случая, чтобы `retry` не сработал. Ощущение "всё падает" было обманчивым —
   это шум от WARN-строк про промежуточные попытки, а не индикатор реальной потери данных.
2. **Настоящая причина "0 файлов" — архитектурная, не про таймауты.** `Semaphore(permits = 1)` был обёрнут
   вокруг *отдельных HTTP-запросов*, а не вокруг обработки группы целиком. Из-за этого все 10 групп, запущенных
   `parallelProcessing`, перехватывали единственный слот семафора друг у друга по кругу: группа А делает свою
   неделю 1, тут же группа Б перехватывает слот на *свою* неделю 1, и так далее. В итоге все группы медленно
   продвигались одновременно, и ни одна не успевала завершиться быстро — при коротких прогонах это выглядело
   как "ничего не сохраняется", хотя данные реально собирались, просто размазанно.

**Итоговое решение** (сочетание нескольких мер, ни одна не сработала бы в одиночку):

- Таймауты `HttpClient` увеличены с 10/30 до 20/60 секунд (`ReaParser`) — сайт местами просто медленный, а не
  всегда "сломанный", и агрессивный таймаут рубит живой, но неторопливый ответ.
- `Semaphore(permits = 1)` перенесён на уровень **всей группы** (`collectSchedule()` целиком), а не отдельных
  запросов — группы теперь обрабатываются последовательно одна за другой вместо параллельного размазывания.
- Общий хелпер `withRetry` (до 5 попыток, экспоненциальная пауза 1-2-4-8-16 секунд) применяется единообразно и
  к `ScheduleCard`, и к `GetDetailsById`, и к сбору списка групп (`Navigator`, главная страница) — раньше
  устойчивость была только у части запросов.
- Пауза (400 мс) между последовательными запросами внутри одной группы — не только ограничение
  одновременности, но и темпа.
- Деградация на двух уровнях: отдельное занятие без преподавателя (если не отдались детали) и отдельная неделя
  без данных (если не отдался `ScheduleCard`) — но *не* вся группа, пока не исчерпан критичный первый запрос.

Это ощутимо медленнее (группы фактически обрабатываются последовательно), но, по цифрам из логов, именно так
удаётся дособрать данные без потерь — сайт просто не рассчитан на скорость быстрее этого.

**Уточнение после ещё одного прогона**: единый бюджет ретраев (5 попыток) оказался неоптимален — обнаружился
конкретный `id` занятия, который сервер не отдавал **никогда** (не транзиентно), и на нём уходило по 3+ минуты
(5 попыток × 20-60 сек), блокируя всю группу целиком (семафор группы держится, пока не решится этот запрос).
Разделил бюджет: **длинный** (5 попыток) — только для первого запроса группы (без него группа теряется целиком,
есть смысл терпеть); **короткий** (2 попытки) — для всего остального (отдельная неделя, детали занятия), где
уже есть безопасная деградация. Так один гарантированно нерабочий `id` стоит секунды, а не минуты, а
`detailsCache` вдобавок делает эту плату разовой на весь прогон (та же лекция у других групп берётся из кэша).
Заодно обернул обход факультетов/курсов/уровней в `ReaGroupEntitiesCollector` в try/catch на каждом уровне —
раньше один не отдавшийся факультет уронил бы сбор групп вообще всех остальных факультетов.

### 7. Номер недели у сайта — свой, не ISO и не чёт/нечет

Сайт нумерует недели последовательно от начала учебного года, а не по международному стандарту (`weekNumber` из
SDK) и не по чётности. Сначала захардкодил дату понедельника 1-й недели вручную (подобрал по пустому ответу
`ScheduleCard?weekNum=1`) — рабочий, но хрупкий вариант, требующий ручного обновления каждый учебный год.
Оказалось, что в этом нет необходимости: запрос с `weekNum=-1` сам резолвит текущую неделю на сервере и
возвращает её реальный номер в скрытом поле `<input id="weekNum">` ответа. Переключился на это — код больше не
зависит от захардкоженной даты.

### 8. Форма обучения и специальность не приходят отдельным полем

`Entity.Extra.educationForm`/`specialty` для группы не покрываются напрямую ни одним полем ответа. Заметил, что
буква сразу после числового префикса в коде группы (`15.28Д-БИО.../26б` / `15.28В-ТПО.../26б`) коррелирует с
формой обучения — подтвердил эвристику (`Д`→"Очная", `В`→"Очно-заочная", `З`→"Заочная") на выборке из 1012
реальных групп разных факультетов. Это эвристика, а не документированное правило сайта — при появлении
незнакомой буквы код возвращает `null`, а не падает.

### Что осталось не проверено на 100%

- Полный прогон `app/Main.kt` по всем 1012 группам (с расписанием и деталями по каждому занятию) не выполнялся
  целиком — это тысячи HTTP-запросов к сайту вуза, и после находки из п.6 гонять его без нужды не хотелось.
  Логика проверена вживую на нескольких группах из разных факультетов/курсов.
- Данные о подгруппах (`data-subgroup` в ответе `GetDetailsById`) собираются в `Schedule.Lesson.subgroups`, но
  пример с реально непустым значением этого поля не встретился — соответствие формату не подтверждено.
